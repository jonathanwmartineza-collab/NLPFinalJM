# Running moderated usability tests (GOV.UK Service Manual)

- Source: Using moderated usability testing — https://www.gov.uk/service-manual/user-research/using-moderated-usability-testing (accessed 2026-11-28)
- Publisher: Government Digital Service (UK), GOV.UK Service Manual
- Licence: OGL-UK-3.0 · Copy in repo: link only

Why this matters for ux-researcher: the NLP Lab and the expert chat are new to most visitors. Watching
a few real people try the live NLTK box, the Prompt coach and the team map is the only E3 evidence
("people did it") this project can produce before grading.

## Key facts: what and when
- Moderated usability testing means watching participants try specific tasks in the service while
  they think aloud, to learn what they do, think and feel.
- Discovery: learn about problems with an existing service. Alpha, beta and live: test prototypes
  or the built service.
- Goals: check people understand what to do and can finish tasks, find specific issues (language,
  layout), and gather ideas.

## Key facts: planning
- Agree research questions, user types and the parts of the service to focus on before booking.
- Recruit actual or likely users.
- Sessions usually last 30 to 60 minutes.
- No more than 6 one-hour sessions a day, at least 15 minutes between sessions, plus lunch.
- One note-taker per session; invite observers; decide whether to record.
- The venue (lab, meeting room, pop-up or remote) must be accessible; arrange interpreters or
  assistants where needed.

## Key facts: tasks and the discussion guide
- Each task sets a clear goal, is relevant and believable, is hard enough to reveal issues, and does
  not give away the answer or hint at the route.
- Several smaller tasks usually beat one large task; order them logically.
- Bring more tasks than needed and choose those most relevant to each participant.
- The discussion guide holds an introduction script, task descriptions and instructions, and a
  planning checklist; dry-run it with a colleague.

## Key facts: running the session
- Let people settle; say you are testing the service, not them.
- Ask a few friendly questions about them so later tasks can be personalised.
- Give clear, neutral instructions; ask them to think aloud; mostly stay quiet.
- Interrupt only to ask about something interesting, to help if they are completely stuck, or to
  ask open follow-ups.
- At the end, clear up what you did not understand and ask for final thoughts; thank them, explain
  next steps, ask for feedback on the session.
- Store personal data (paper or recordings) securely at the end of the day.

## Key facts: data and assistive technology
- Real personal data engages people more, but only if the service can process and secure it;
  otherwise use dummy data and a made-up character.
- People using assistive technology should use their own devices; learn how the technology works
  beforehand so you can tell a service problem from a technology problem.

## How to apply it here
- Research question as a decision, e.g. "We need to know whether visitors can run the live NLTK
  analysis and read its results, so we can decide whether the panel labels need rewriting."
- Tasks that never use the UI's labels: "You pasted a product review and want to know whether it
  sounds positive. Find out." (not "Click Analyze").
- Session plan: 30 minutes, 4 to 6 tasks covering chat, /nlp live box, Prompt coach, Library search.
- Note-taker logs task success (yes / partial / no), time, errors and quotes against P-codes.
- Include at least one screen-reader or keyboard-only participant on their own setup.
- No real personal data is needed: the site stores nothing, so tasks use sample texts.

## Limits
- The page gives no participant count and does not cover analysis; see the GOV.UK research
  analysis guide or the shared product discovery note.
- Last updated 3 October 2017; remote testing is only mentioned as an option.
